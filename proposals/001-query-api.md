## 9. Post-implementation follow-up (verified 2026-05-19 against wren.aemwip.com)

`POST /api/v1/{collection}/_query` and `/_materialized` shipped. Verified working
against the `tkd` `events` collection:

- Projection `{"select":[...]}` → slim docs ✅
- `count` / `countDistinct` over deep unnest paths grouped by `$documentId`
  (`count: report.divisions[].categories[].ranked[].gmsId` → 742 for Spanish
  Open; `countDistinct …ranked[].country` → 56) ✅
- Shallow `where` with `~*` (`name ~* president`) ✅
- Materialized queries persist + auto-refresh ✅

Two gaps block full elimination of the app's hand-built `index.json`
(the 503 KB `countryCounts` / `tcCounts` / `gmsIds` roll-up) and the
cross-event name/club search:

### 9.1 `groupBy` on a deep (unnest) array path yields a `null` key

```
POST /api/v1/events/_query
{"aggregate":{"groupBy":["$documentId","report.divisions[].categories[].ranked[].country"],
              "metrics":{"n":{"count":"report.divisions[].categories[].ranked[].gmsId"}}}}
→ rows: [{ "key": { "$documentId":"…", "report.divisions[].categories[].ranked[].country": null }, "n":742 }, …]
```

The `count` metric unnests correctly, but the parallel deep path used as a
**group key** resolves to `null` instead of unnesting. Per-country / per-team
breakdowns (the bulk of the index doc) therefore can't be produced. Expected:
the group key unnests the same way metric paths do (one row per distinct
`country` per document).

### 9.2 Deep array paths rejected in `where`

```
POST /api/v1/events/_query
{"where":"report.divisions[].categories[].ranked[].name ~* khavari","select":["name"]}
→ {"error":"Invalid filter path: report.divisions[].categories[].ranked[].name"}
```

`where` accepts shallow top-level paths only; the same `[]` unnest grammar that
aggregation accepts is rejected here. This blocks cross-event athlete
name/club/team search (the feature deferred for index-size reasons).

### Impact

With 9.1 + 9.2 closed, the app deletes `index.json` entirely and the
name/club search becomes a single query — the original goals of this proposal.
Until then the app keeps the hand-built roll-up for breakdowns and can adopt
`_query` only for the slim metadata list.

## 1. Problem

Apps built on Wren that need **cross-document views** are forced to hand-maintain a
denormalised aggregate document (an "index doc") because the read API can only
return whole documents one at a time.

Concrete case — the taekwondo app stores one document per tournament:

```
events/<slug>  →  { name, startDate, …, report: { divisions:[ { categories:[
                     { ranked:[ {gmsId,name,country,club,team,points,…} ],
                       unranked:[ … ] } ] } ] } }
```

~30 event documents, 50–200 KB each. The SPA needs an **overview** ("list every
event with per-country / per-team / per-watchlist athlete counts") and
**search** ("which events is athlete X / club Y in"). Neither is expressible
against Wren, so the app builds `events/data/index.json` — a flattened roll-up
of every event regenerated by a build script on every data change.

Consequences, all of which are general Wren problems, not app problems:

- **Write amplification** — every new view dimension (country counts → team/club
  counts → gmsId lists → name search) is another field baked into the index doc.
  It has grown to **~503 KB** and is loaded in full on first paint.
- **Staleness & duplication** — the index is a second source of truth that must
  be rebuilt and redeployed in lockstep with the real documents.
- **No use of Wren's strengths** — versioning, labels, time-travel and row-level
  scope do not extend to the hand-built index; it is just a blob.
- **Every Wren app reinvents this.** The "list-then-find-then-put idiom that
  every ingestion script otherwise reinvents" (openapi.yaml:472) has a read-side
  twin: the index-doc idiom.

The existing `?filter` + `?facets` get close but stop short:

| Capability | Today | Needed |
|---|---|---|
| Filter by JSON path | ✅ `?filter` | ✅ keep |
| Facet counts on top-level fields | ✅ `?facets` | ⚠️ extend |
| **Return only selected fields** (projection) | ❌ | ✅ **required** |
| **Aggregate across/within nested arrays** (`report.divisions[].categories[].ranked[].gmsId`) | ❌ | ✅ **required** |
| **Group-by document with computed metrics** | ❌ | ✅ **required** |
| Versioned / labelled / time-travel queries | partial (`?label` on list) | ✅ must apply to all of the above |

Without **projection**, even a perfect filter still returns full 200 KB docs, so
the overview cannot be built from a query. Projection + aggregation together are
what eliminate the index doc.

---

## 2. Goals / non-goals

**Goals**

1. Make the index-doc idiom unnecessary: an app can derive any overview/search
   view from a query at read time.
2. One coherent query surface — filter, projection, aggregation — reusing the
   existing filter grammar, not a second DSL.
3. Versioning-native: every query honours `?label` / `asOf` and row-level scope,
   exactly like single-doc reads.
4. Stay fast on Postgres JSONB without forcing every app to think about indexes
   (sensible defaults + an opt-in index declaration).
5. LLM-friendly: JSON-in/JSON-out, predictable shapes, documented in openapi.yaml.

**Non-goals**

- A general SQL endpoint. The query language stays a constrained, safe,
  JSON-expressible structure (no arbitrary SQL injection surface, no joins
  across collections in v1).
- Write-side materialisation is **out of scope for v1** (see §7 — it becomes
  trivial once the query language exists, and is the natural follow-up rather
  than a competing design).

## 3. Proposed API

A single new verb on the existing collection endpoints: **query**. Expressed as
`POST /api/v1/{collection}/_query` (and the org-scoped/tree equivalents) so the
query body is structured JSON rather than an overloaded query string. `GET`
with `?filter=` stays as the simple-case shorthand and is defined as sugar for a
query body.

```
POST /api/v1/{collection}/_query
POST /api/v1/orgs/{slug}/{collection}/_query
```

### 3.1 Request body

```jsonc
{
  "where":   <filter-expr>,         // reuse the existing ?filter grammar
  "select":  ["startDate","name","report.divisions[].name"],   // projection
  "aggregate": {                    // optional; when present, response is rows of metrics
     "groupBy": ["$documentId"],    // or any json path; $documentId / $path are pseudo-paths
     "metrics": {
        "athletes":   { "count": "report.divisions[].categories[].ranked[].gmsId" },
        "byCountry":  { "countDistinct": "report..ranked[].gmsId",
                        "by": { "expr": "substringBefore(report..ranked[].gmsId,'-')" } },
        "teamClub":   { "countDistinct": "$athlete",
                        "by": { "concat": ["report..ranked[].team","report..ranked[].club"] } }
     }
  },
  "label":   "published",           // versioned read (optional) — same semantics as single-doc
  "asOf":    "2026-05-01T00:00:00Z",// time-travel (optional)
  "limit":   100,
  "cursor":  "…"
}
```

- **`select`** — projection. Dot/`[]` path syntax already used by `?filter`.
  Returns documents pruned to those paths (arrays preserved structurally). This
  alone replaces "fetch every event doc to build a list".
- **`aggregate`** — when present the response is **metric rows**, not documents.
  - `groupBy` accepts json paths plus pseudo-paths `$documentId`, `$path`,
    `$collection`.
  - Metric ops (v1 set): `count`, `countDistinct`, `sum`, `min`, `max`, `avg`.
  - Array paths with `[]` are **unnested** before aggregation — this is the key
    capability: aggregate over `report.divisions[].categories[].ranked[]`
    without the app flattening it first.
  - `by` sub-grouping with a small expression vocabulary
    (`substringBefore/After`, `concat`, `lower`, `coalesce`) covers the
    real cases (country = prefix of gmsId, team␟club key) without a full
    expression language.
- **`where` / `label` / `asOf`** — identical semantics to existing reads;
  queries are just multi-document reads, so versioning & scope already have a
  defined meaning and must be preserved.

### 3.2 Response

Projection mode:

```jsonc
{ "items": [ { "id":"…", "path":"events/spanish-open-2026",
               "data": { "name":"…","startDate":"…", "report":{…pruned…} } } ],
  "cursor": "…" }
```

Aggregate mode:

```jsonc
{ "rows": [
    { "key": { "$documentId":"…", "$path":"events/spanish-open-2026" },
      "athletes": 691,
      "byCountry": { "SUI": 7, "GER": 21, … },
      "teamClub":  { "switzerland national team␟…": 3, … } } ],
  "cursor": "…" }
```

The taekwondo overview becomes exactly one call and `index.json` is deleted:

```jsonc
POST /api/v1/orgs/tkd/events/_query
{ "select": ["name","startDate","endDate","city","country","regDeadline"],
  "aggregate": {
     "groupBy": ["$path"],
     "metrics": {
       "athletes":  { "count": "report.divisions[].categories[].ranked[].gmsId" },
       "byCountry": { "countDistinct":"report..ranked[].gmsId",
                      "by":{ "substringBefore":["report..ranked[].gmsId","-"] } } } } }
```

Name / club / team search across all events (the feature we just declined for
cost reasons) becomes free:

```jsonc
POST /api/v1/orgs/tkd/events/_query
{ "where": "report..ranked[].name ~* 'khav'",
  "select": ["name","report.divisions[].categories[].name",
             "report..ranked[?(@.name ~* 'khav')]"] }
```

## 4. Postgres implementation sketch

Wren already stores `data JSONB` with a GIN index
(`versions_data_gin_idx`, tenant/001). The query engine compiles the JSON query
body to parameterised SQL — never string-concatenated user SQL.

- **Projection** → `jsonb_build_object` / `jsonb_path_query` over the selected
  paths; cheap, no schema needed.
- **Array aggregation** → `jsonb_path_query` / `LATERAL jsonb_array_elements`
  to unnest `[]` segments, then standard `count/sum/...` + `GROUP BY`.
- **Filter** → existing compiler; `~*` (regex/ILIKE) for substring search.
- **Indexes** — keep the catch-all GIN for containment filters; add an **opt-in
  index declaration** on the collection schema so hot paths are fast:

  ```jsonc
  // PUT /api/v1/{collection}/_schema  (extend existing wrapper)
  { "schema": {…},
    "indexes": [
      { "path": "report..ranked[].gmsId",  "kind": "btree-unnest" },
      { "path": "report..ranked[].name",   "kind": "trigram" }   // pg_trgm for ~*
    ] }
  ```

  Implemented as expression / `jsonb_path_ops` GIN / `pg_trgm` indexes. Default
  (no declaration) still works via the existing GIN, just slower — same
  performance contract as today's `?filter`.

- **Versioning** — queries run against the same resolved-current-state view
  single-doc reads use; `label`/`asOf` select the version per document before
  the query is applied. Row-level scope (`access`, `filter_expr`) is applied as
  an outer predicate exactly as `filterResponse` does today
  (sandbox/index.ts:1044) — **no query may widen visibility**.

## 5. Security & versioning interactions

- Per-permission `filterExpr`/`labelFilter` (sandbox/index.ts:594) MUST wrap the
  query as an enclosing constraint; projection/aggregate run **after** scope is
  applied so an aggregate can never count documents/fields the caller can't read.
- Field-level permissions: a `select`/metric referencing a field the role can't
  read is dropped (projection) or rejected (aggregate) — never silently leaked.
- Audit: a query read is one audited read event with the query body recorded
  (consistent with `audit_reads`).
- Result-size limits: hard cap on `select` breadth and `groupBy` cardinality;
  `limit`/`cursor` mandatory beyond a threshold; query timeout. Prevents the
  endpoint becoming a DoS or a full-table-scan footgun.

## 6. Backward compatibility

- Purely additive. `GET /{collection}?filter=…&facets=…` stays and is
  redefined as sugar over `_query` (`facets` → an `aggregate.metrics` count).
- No data migration. No change to storage. Existing apps untouched.
- Docs-in-sync (project rule): this lands with **openapi.yaml**, **README**
  ("API (simplified)" block), **client-ts** (`resources/documents.ts`,
  `types.ts` already reference `facets`), **client-py**, and the marketing
  tutorial if the admin UI surfaces it.

## 7. Phasing (full target, not a partial shortcut)

The end state is the full filter+project+aggregate query API. Phasing is purely
delivery order, each phase independently shippable and useful:

1. **Projection** (`select`) on the query endpoint. Immediately lets the
   taekwondo overview drop the bulk of `index.json` (fetch slim event list).
2. **Aggregation** (`groupBy` + metrics, array unnest). Eliminates `index.json`
   entirely; enables name/club/team search with zero client bloat.
3. **Index declarations** on collection schema for hot paths (perf hardening).
4. **Materialised query** (a named, persisted query whose result is kept fresh
   on write) — the index-doc pattern, now owned by Wren and versioned like any
   document. Trivial once 1–3 exist; this is *why* projection+aggregate is the
   right foundation rather than a bespoke "computed field" feature.

Stopping after phase 1 would be the quick/partial option and is explicitly
**not** the recommendation — phases 2–4 are what make Wren a versioned
*queryable* store rather than a versioned blob store.

---

## 8. Risks / open questions

- Query-language scope creep → mitigate with a fixed v1 op set (§3.1) and an
  explicit "no joins, no arbitrary expressions" line.
- JSONB aggregation cost on large collections → index declarations (§4) +
  mandatory limits (§5); document the performance contract.
- Path grammar must be one spec shared by `where`, `select`, `groupBy`,
  index declarations, and field-permission rules — pick the existing `?filter`
  path syntax as the single source of truth.
- Pseudo-paths (`$documentId`,`$path`,`$collection`,`$athlete` for "current
  unnested element") need a precise definition before implementation.
